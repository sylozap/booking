# План реализации по фазам

Детализация до уровня задач — [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).

Принцип: **вертикальный срез до полной готовности, затем ширина**
([ADR-0009](adr/0009-delivery-and-infrastructure.md)). Фаза считается закрытой только
по критериям «Готово, когда» — не «код написан».

## Фаза 0. Каркас

- монорепозиторий: `services/`, `libs/chassis/`, `deploy/`, `docs/`
- локальная инфраструктура в Docker Compose: PostgreSQL, Redis, Kafka (KRaft),
  OTel Collector, Prometheus, Loki, Tempo, Grafana, Mailhog
- инструментарий: линтер, форматтер, типы, pre-commit, Makefile
- kind/k3d кластер, ArgoCD, ghcr.io

**Готово, когда:** `make up` поднимает всю инфраструктуру локально, Grafana открыта,
пустой кластер с ArgoCD работает.

## Фаза 1. `identity` — вертикальный срез

Регистрация, вход, OAuth Google, JWT (RS256, JWKS-эндпоинт), ротация refresh с
обнаружением переиспользования, RBAC по тенантам, `/users/me`.

Полная обвязка: миграции, health/readiness, структурные логи с `trace_id`, метрики
RED, трассировка, unit + интеграционные тесты (testcontainers), Dockerfile,
GitHub Actions, манифесты, ArgoCD-приложение.

**Готово, когда:** сервис задеплоен в кластер через GitOps; запрос виден в Tempo,
его логи находятся по `trace_id` в Loki, метрики в Grafana; тесты и деплой идут из
пайплайна без ручных шагов.

## Фаза 2. Извлечение шасси

Вынести из `identity` инфраструктуру в `libs/chassis`: логирование, OTel,
конфигурация, ошибки, health, аутентификация по JWKS, outbox (запись + relay),
идемпотентное потребление. `identity` переводится на шасси и остаётся зелёным.

**Готово, когда:** `identity` работает на шасси, новый сервис-заготовка поднимается
с полной телеметрией за считанные часы.

## Фаза 3. `catalog`

Организации, специалисты, услуги, `specialist_services`. Публикация
`OfferingUpdated` / `OfferingDeactivated` через outbox.

**Готово, когда:** событие с разрешёнными эффективными значениями видно в топике;
пайплайн и наблюдаемость такие же, как у `identity`.

## Фаза 4. `booking` — ядро

Проекция `offerings` из событий `catalog` (включая холодное наполнение
воспроизведением топика). Рабочие часы, исключения. Алгоритм доступности с DST.
Ограничение `EXCLUDE`. Создание брони с `Idempotency-Key`. Отмена и перенос.
Sweeper истёкших удержаний. Кэш доступности в Redis с инвалидацией.

**Готово, когда:** параллельный нагрузочный тест на один слот даёт ровно одну бронь
и остальные 409; тесты на переход DST зелёные; остановка Redis не нарушает
корректность; перестроение проекции с нуля воспроизведением топика работает.

## Фаза 5. `payment` и сага

Stripe в тестовом режиме: PaymentIntent с ручным списанием, вебхуки с
дедупликацией. Сага: `BookingHeld` → авторизация → `CONFIRMED` → capture.
Компенсации: void при истечении, возврат при отмене, обработка гонки «авторизация
после истечения».

**Готово, когда:** все ветки саги воспроизведены тестами, включая гонку и повторную
доставку вебхука; ни один сценарий не оставляет деньги списанными без подтверждённой
брони.

## Фаза 6. `notification`

Consumer событий, шаблоны, email через SMTP (Mailhog локально), адаптеры-заглушки
SMS и push, ретраи, dead letter.

**Готово, когда:** полный путь «бронь → оплата → письмо» проходит end-to-end;
остановленный `notification` не влияет на бронирование, а после запуска
дочитывает накопленное.

## Фаза 7. Эксплуатационная зрелость

Алерты (5xx, лаг потребителей, застрявший outbox, неработающий sweeper, отказы
вебхуков). Дашборды по сервисам и по саге. Нагрузочное тестирование доступности.
Проверки отказов: убить `payment`, убить брокер, убить Redis — зафиксировать
фактическое поведение системы. Runbook.

**Готово, когда:** для каждого отключённого компонента задокументировано, что именно
деградирует и что продолжает работать.

## Что вне плана

См. [ADR-0010](adr/0010-mvp-scope.md): повторяющиеся записи, отзывы, чёрные списки,
S3, геопоиск, Stripe Connect, мультивалютность, гостевые брони.
