# План реализации

Иерархия: **Фаза → Milestone → Feature → Task**. Задача считается закрытой только по
критерию «Готово, когда» — не по факту написанного кода.

Формат идентификатора: `P<фаза>-T<номер>`. Зависимости указывают на задачи, без
которых текущая не может быть проверена.

Сквозные ограничения, действующие для **каждой** задачи и далее не повторяемые:

- слоистость `api → application → domain → infrastructure`, зависимости только внутрь
  ([ADR-0016](adr/0016-service-structure-and-data-topology.md), D39);
- никаких импортов между сервисами; общее — только шасси и контракты событий
  ([ADR-0009](adr/0009-delivery-and-infrastructure.md), D7);
- никаких синхронных межсервисных вызовов ([ADR-0001](adr/0001-microservice-boundaries.md));
- любая публикация события — только через outbox в одной транзакции с изменением
  состояния ([ADR-0005](adr/0005-event-driven-integration.md), D19);
- `tenant_id` фильтруется в репозитории всегда (D40);
- новый эндпоинт отдаёт ошибки в `problem+json` (D43).

# Фаза 1 — `identity` как вертикальный срез

Цель: один сервис, доведённый до полного production-состояния. Всё, что здесь

**`P1-T01` — Скелет приложения по слоям**
- **Описание:** FastAPI-приложение, каталоги `api/`, `application/`, `domain/`, `infrastructure/`, точка входа, роутер версии `/api/v1`.
- **Зависит:** P0-T05
- **Файлы:** `services/identity/`
- **Готово:** приложение стартует, `/api/v1` смонтирован
- **Тесты:** smoke-тест старта приложения
- **Ограничения:** D39, D45

**`P1-T02` — Конфигурация с fail-fast**
- **Описание:** `pydantic-settings`, только переменные окружения, падение при старте с невалидной или неполной конфигурацией.
- **Зависит:** P1-T01

- **Тесты:** unit на валидацию, на отсутствие переменной, на неверный тип

# Фаза 2 — Service chassis

Цель: превратить инфраструктуру `identity` в переиспользуемую библиотеку, после чего
каждый следующий сервис стоит кратно дешевле. Фаза не добавляет функциональности —
её результат проверяется тем, что `identity` остаётся полностью зелёным.

## M2.1 — Извлечение сквозной инфраструктуры

**`P2-T01` — Логирование и маскирование**
- **Описание:** перенос из `identity` в `chassis.logging`, конфигурируемый список чувствительных полей.
- **Зависит:** P1-T04
- **Файлы:** `libs/chassis/logging/`, `services/identity/`
- **Готово:** `identity` не содержит собственной настройки логирования; тесты маскирования переехали в шасси
- **Тесты:** unit шасси на маскирование; регресс `identity` зелёный
- **Ограничения:** D7 (только инфраструктура), D50

**`P2-T02` — Телеметрия и health**
- **Описание:** `chassis.telemetry` — трассировка, метрики, `/healthz`, `/readyz` с настраиваемым набором проверок.
- **Зависит:** P2-T01, P1-T06, P1-T07
- **Файлы:** `libs/chassis/telemetry/`
- **Готово:** подключение одной функцией даёт сервису трассировку, метрики и оба эндпоинта
- **Тесты:** интеграционный на минимальном тестовом приложении
- **Ограничения:** D8

**`P2-T03` — Конфигурация**
- **Описание:** `chassis.config` — базовые настройки (БД, Redis, Kafka, телеметрия), fail-fast, расширение в сервисе.
- **Зависит:** P2-T02, P1-T02
- **Файлы:** `libs/chassis/config/`
- **Готово:** сервис объявляет только свои специфичные поля; общие наследуются
- **Тесты:** unit на наследование и на падение при неполной конфигурации
- **Ограничения:** D54

**`P2-T04` — Ошибки**
- **Описание:** `chassis.errors` — базовые доменные исключения, обработчик problem+json, общий каталог кодов с возможностью расширения.
- **Зависит:** P2-T03, P1-T03
- **Файлы:** `libs/chassis/errors/`
- **Готово:** сервис регистрирует свои коды, формат ответа единый во всех сервисах
- **Тесты:** unit на маппинг; контрактный тест формата ответа
- **Ограничения:** D43

**`P2-T05` — Аутентификация потребителя токена**
- **Описание:** `chassis.auth` — валидация JWT по кэшированному JWKS, проверка denylist, зависимости для permission с учётом тенанта.
- **Зависит:** P2-T04, P1-T20, P1-T21
- **Файлы:** `libs/chassis/auth/`
- **Готово:** сервис без собственного кода аутентификации отклоняет невалидный токен и проверяет право; кэш JWKS обновляется по TTL и при неизвестном `kid`
- **Тесты:** unit на кэш и обновление ключей; интеграционный на отказ по праву; тест на ротацию ключа
- **Ограничения:** D22, D26, D53

## M2.2 — Событийная инфраструктура

**`P2-T06` — Outbox: запись**
- **Описание:** `chassis.outbox` — модель, миграционный фрагмент, API записи события строго в текущей транзакции.
- **Зависит:** P2-T03
- **Файлы:** `libs/chassis/outbox/`
- **Готово:** попытка записать событие вне транзакции завершается ошибкой; откат транзакции откатывает и событие
- **Тесты:** интеграционные на атомарность и на запрет вне транзакции
- **Ограничения:** D19, D5

**`P2-T07` — Outbox: relay**
- **Описание:** процесс публикации неотправленных событий в Kafka, порядок по `occurred_at`, ретраи, метрики лага и размера очереди.
- **Зависит:** P2-T06, P0-T08
- **Файлы:** `libs/chassis/outbox/relay.py`
- **Готово:** при недоступном брокере события накапливаются и публикуются после восстановления без потерь и без нарушения порядка внутри ключа
- **Тесты:** интеграционные на восстановление после отказа брокера, на порядок, на метрику лага
- **Ограничения:** D31 (ключ партиционирования), D5

**`P2-T08` — Идемпотентное потребление**
- **Описание:** `chassis.consumer` — консьюмер с дедупликацией по `event_id`, ретраями и отправкой в DLQ после исчерпания попыток.
- **Зависит:** P2-T07
- **Файлы:** `libs/chassis/consumer/`
- **Готово:** повторная доставка того же события не приводит к повторному эффекту; необрабатываемое событие попадает в DLQ, а не блокирует партицию бесконечно
- **Тесты:** интеграционные на дубликат, на транзиентную ошибку с ретраем, на попадание в DLQ
- **Ограничения:** D18, D5

**`P2-T09` — Контракты событий**
- **Описание:** `contracts/` — JSON Schema каждого события с версией, генерация типов, валидация при публикации и при потреблении.
- **Зависит:** P2-T08
- **Файлы:** `contracts/events/`, `libs/chassis/contracts/`
- **Готово:** публикация события, не соответствующего схеме, отклоняется; неизвестные поля при чтении игнорируются
- **Тесты:** контрактные тесты обеих сторон; тест на tolerant reader
- **Ограничения:** D59, D5 (версионирование)

## M2.3 — Фоновые задачи и оснастка

**`P2-T10` — Планировщик с защитой от дублей**
- **Описание:** `chassis.jobs` — периодические задачи внутри отдельного процесса, взаимное исключение через advisory lock PostgreSQL, метрика последнего успешного прогона.
- **Зависит:** P2-T03
- **Файлы:** `libs/chassis/jobs/`
- **Готово:** при двух репликах задача выполняется одной; остановка задачи видна по метрике «время с последнего прогона»
- **Тесты:** интеграционный с двумя параллельными процессами; тест на метрику
- **Ограничения:** D57

**`P2-T11` — Тестовая оснастка**
- **Описание:** фикстуры testcontainers (PostgreSQL, Kafka, Redis), фабрики токенов, помощник для проверки опубликованных событий.
- **Зависит:** P2-T09
- **Файлы:** `libs/chassis/testing/`
- **Готово:** интеграционный тест нового сервиса пишется без собственной инфраструктурной обвязки
- **Тесты:** самотестирование фикстур
- **Ограничения:** D59

**`P2-T12` — Перевод `identity` на шасси**
- **Описание:** удаление продублированного кода, переход на компоненты библиотеки.
- **Зависит:** P2-T05, P2-T11
- **Файлы:** `services/identity/`
- **Готово:** в сервисе не осталось собственной инфраструктуры; весь набор тестов фазы 1 зелёный; развёртывание проходит
- **Тесты:** полный регресс фазы 1
- **Ограничения:** D7

**`P2-T13` — Шаблон сервиса**
- **Описание:** заготовка нового сервиса на шасси: слои, конфигурация, телеметрия, миграции, Dockerfile, манифесты, заготовки тестов.
- **Зависит:** P2-T12
- **Файлы:** `scripts/new_service/`
- **Готово:** созданный из шаблона пустой сервис поднимается в кластере с трассировкой, метриками и health-эндпоинтами
- **Тесты:** прогон генерации в CI
- **Ограничения:** D6

# Фаза 4 — `booking`

Цель: ядро домена. Здесь живёт главный инвариант системы, и здесь же —
самая высокая плотность нетривиальных решений.

## M4.3 — Расчёт доступности

**`P4-T06` — Развёртывание шаблона по датам**
- **Описание:** чистая функция: недельный шаблон + диапазон дат → интервалы в локальной зоне.
- **Зависит:** P4-T04
- **Файлы:** `services/booking/domain/availability/expand.py`
- **Готово:** функция не обращается к БД и брокеру, тестируется изолированно
- **Тесты:** unit на границы диапазона, на пустой шаблон, на неполную неделю
- **Ограничения:** D39 (домен без инфраструктуры)

**`P4-T07` — Применение исключений**
- **Описание:** вычитание `TIME_OFF`, добавление `EXTRA_SHIFT`, слияние пересечений.
- **Зависит:** P4-T06
- **Файлы:** `services/booking/domain/availability/exceptions.py`
- **Готово:** исключение, покрывающее весь день, обнуляет доступность; смежные интервалы сливаются
- **Тесты:** unit на частичное перекрытие, полное перекрытие, добавление смены вне графика
- **Ограничения:** —

**`P4-T08` — Конвертация в UTC и обработка DST**
- **Описание:** перевод локальных интервалов в UTC по IANA-зоне; несуществующее время усекается, дублирующееся берётся по первому вхождению.
- **Зависит:** P4-T07
- **Файлы:** `services/booking/domain/availability/timezone.py`
- **Готово:** результат корректен в дни весеннего и осеннего перехода, включая зоны южного полушария
- **Тесты:** unit на дату весеннего перехода, осеннего перехода, обычный день, зону без DST — **обязательный набор**
- **Ограничения:** D13

**`P4-T09` — Вычитание занятых интервалов**
- **Описание:** удаление интервалов существующих броней (`HELD`, `CONFIRMED`), уже включающих буфер.
- **Зависит:** P4-T08, P4-T13
- **Файлы:** `services/booking/domain/availability/subtract.py`
- **Готово:** бронь в середине рабочего дня разбивает интервал на два; буфер не учитывается дважды
- **Тесты:** unit на разбиение, на примыкание, на полное перекрытие
- **Ограничения:** D12 (буфер в интервале)

**`P4-T10` — Нарезка сеткой**
- **Описание:** нарезка свободных интервалов шагом 15 минут с учётом длительности и буфера, отсечение прошлого, `min_lead_time` 2 часа, горизонт 60 дней.
- **Зависит:** P4-T09
- **Файлы:** `services/booking/domain/availability/slots.py`
- **Готово:** слот выдаётся только если в него помещается услуга целиком вместе с буфером
- **Тесты:** unit на границу помещаемости, на `min_lead_time`, на горизонт
- **Ограничения:** D27

**`P4-T11` — Эндпоинт доступности**
- **Описание:** `GET /availability` с ограничением диапазона 30 дней, ответ в UTC.
- **Зависит:** P4-T10
- **Файлы:** `services/booking/api/availability.py`
- **Готово:** эндпоинт публичен; превышение диапазона отклоняется; неактивное предложение даёт пустой результат
- **Тесты:** интеграционные на ограничение диапазона, на неактивное предложение, на несуществующего специалиста
- **Ограничения:** D11, D45

**`P4-T12` — Кэш доступности**
- **Описание:** кэш в Redis по ключу «специалист + дата», TTL 60 секунд, инвалидация по событиям брони и изменениям расписания, защита от одновременного пересчёта.
- **Зависит:** P4-T11, P4-T14
- **Файлы:** `services/booking/infrastructure/cache.py`
- **Готово:** создание брони немедленно убирает слот из выдачи; полная остановка Redis не влияет на корректность, только на латентность
- **Тесты:** интеграционные на инвалидацию, на работу без Redis, на параллельные запросы одного ключа
- **Ограничения:** D25 — путь записи не обращается к кэшу

## M4.4 — Брони

**`P4-T13` — Таблица броней и инвариант**
- **Описание:** `bookings`, ограничение `EXCLUDE USING gist` с условием по статусам, уникальность ключа идемпотентности, индексы из DOMAIN.md.
- **Зависит:** P4-T01
- **Файлы:** `services/booking/migrations/`, `infrastructure/db/models.py`
- **Готово:** прямая вставка пересекающейся брони из psql отклоняется базой
- **Тесты:** интеграционный на отклонение пересечения на уровне БД, минуя приложение
- **Ограничения:** D12

**`P4-T14` — Создание брони**
- **Описание:** `POST /bookings` с `Idempotency-Key`: проверка рабочих часов и предложения, вставка `HELD` с `hold_expires_at`, публикация `BookingHeld`.
- **Зависит:** P4-T13, P4-T10, P4-T02
- **Файлы:** `services/booking/api/bookings.py`, `application/create_booking.py`
- **Готово:** повторный запрос с тем же ключом возвращает ту же бронь; снапшот цены и длительности зафиксирован в записи
- **Тесты:** интеграционные на идемпотентность, на бронь вне рабочих часов, на неактивное предложение, на фиксацию снапшота
- **Ограничения:** D18, D12, ADR-0004

**`P4-T15` — Конкурентное бронирование**
- **Описание:** перехват `ExclusionViolation` в репозитории и преобразование в доменное `SlotAlreadyTaken` → 409 `slot_taken`.
- **Зависит:** P4-T14
- **Файлы:** `services/booking/infrastructure/repositories/booking.py`
- **Готово:** параллельные запросы на один слот дают ровно одну бронь, остальные — 409 с доменным кодом; ошибка БД наружу не протекает
- **Тесты:** интеграционный с параллельными запросами (**обязательный**)
- **Ограничения:** D12, D43

**`P4-T16` — Отмена**
- **Описание:** `POST /bookings/{id}/cancel`; клиент — не позже `min_lead_time`, специалист — в любой момент; публикация `BookingCancelled` с признаком необходимости возврата.
- **Зависит:** P4-T14
- **Файлы:** `services/booking/application/cancel_booking.py`
- **Готово:** правило времени применяется только к клиенту; повторная отмена не порождает второй возврат
- **Тесты:** интеграционные на оба субъекта, на нарушение срока, на повторную отмену
- **Ограничения:** D28

**`P4-T17` — Перенос**
- **Описание:** `POST /bookings/{id}/reschedule` — освобождение старого и занятие нового интервала в одной транзакции, платёж не затрагивается.
- **Зависит:** P4-T15
- **Файлы:** `services/booking/application/reschedule_booking.py`
- **Готово:** при занятости нового интервала старый остаётся за клиентом, изменений нет
- **Тесты:** интеграционные на успешный перенос, на занятый новый слот, на атомарность отката
- **Ограничения:** D16

**`P4-T18` — Отметка неявки**
- **Описание:** перевод в `NO_SHOW` специалистом после начала брони, без возврата.
- **Зависит:** P4-T14
- **Файлы:** `services/booking/application/no_show.py`
- **Готово:** статус доступен только специалисту брони и только после времени начала; событие возврата не публикуется
- **Тесты:** интеграционные на права, на преждевременную отметку, на отсутствие возврата
- **Ограничения:** D29

**`P4-T19` — Списки броней**
- **Описание:** `GET /bookings` с курсорной пагинацией и областью видимости по роли: клиент — свои, специалист — свои, `ORG_ADMIN` — организации.
- **Зависит:** P4-T14
- **Файлы:** `services/booking/api/bookings.py`
- **Готово:** ни одна роль не видит чужие брони; курсор устойчив к вставкам
- **Тесты:** обязательные тесты видимости для каждой роли; тест пагинации при конкурентной вставке
- **Ограничения:** D44, D40

# Фаза 5 — `payment` и сага оплаты

Цель: распределённая транзакция с компенсациями, доведённая до состояния, в котором
ни один сценарий отказа не оставляет деньги списанными без подтверждённой брони.

## M5.1 — Каркас и интеграция со Stripe

**`P5-T01` — Каркас сервиса**
- **Описание:** генерация из шаблона, база `payment`, таблицы `payments` и `webhook_events`, манифесты.
- **Зависит:** P2-T13
- **Файлы:** `services/payment/`, `deploy/k8s/base/payment/`
- **Готово:** сервис развёрнут; уникальность по `booking_id` и по `provider_event_id` обеспечена базой
- **Тесты:** интеграционный на ограничения уникальности
- **Ограничения:** D18

**`P5-T02` — Клиент Stripe**
- **Описание:** обёртка над API: таймауты, ретраи только идемпотентных операций, ключ идемпотентности Stripe, тестовые ключи в секретах.
- **Зависит:** P5-T01, P0-T15
- **Файлы:** `services/payment/infrastructure/stripe_client.py`
- **Готово:** повторный вызов при сетевой ошибке не создаёт второй платёж; секреты не попадают в логи
- **Тесты:** интеграционные с заглушкой на таймаут и повтор; проверка отсутствия ключей в логах
- **Ограничения:** D50, ADR-0004

## M5.2 — Прямой путь саги

**`P5-T03` — Авторизация платежа**
- **Описание:** потребитель `BookingHeld` → создание PaymentIntent с ручным списанием → публикация `PaymentAuthorized` либо `PaymentFailed`.
- **Зависит:** P5-T02, P2-T08
- **Файлы:** `services/payment/application/consumers/booking_held.py`
- **Готово:** повторная доставка `BookingHeld` не создаёт второй PaymentIntent
- **Тесты:** интеграционные на успех, на отказ карты, на дубликат события
- **Ограничения:** D14, D18

**`P5-T04` — Приём вебхуков**
- **Описание:** `POST /webhooks/stripe`: проверка подписи, запись в `webhook_events`, дедупликация, преобразование в доменные события.
- **Зависит:** P5-T03
- **Файлы:** `services/payment/api/webhooks.py`
- **Готово:** неверная подпись отклоняется; повторная доставка того же события не даёт повторного эффекта; неизвестный тип события не приводит к ошибке
- **Тесты:** интеграционные на подпись, на дубликат, на неизвестный тип
- **Ограничения:** D18

**`P5-T05` — Подтверждение брони**
- **Описание:** в `booking` — потребитель `PaymentAuthorized`: `HELD` → `CONFIRMED`, публикация `BookingConfirmed`.
- **Зависит:** P5-T03, P4-T14
- **Файлы:** `services/booking/application/consumers/payment.py`
- **Готово:** подтверждение идемпотентно; бронь в неподходящем статусе не меняется молча
- **Тесты:** интеграционные на подтверждение, на дубликат, на неверный исходный статус
- **Ограничения:** D15, D18

**`P5-T06` — Списание средств**
- **Описание:** потребитель `BookingConfirmed` → capture → публикация `PaymentCaptured`.
- **Зависит:** P5-T05
- **Файлы:** `services/payment/application/consumers/booking_confirmed.py`
- **Готово:** двойное списание невозможно при повторной доставке события
- **Тесты:** интеграционные на списание и на дубликат
- **Ограничения:** D14

## M5.3 — Компенсации и гонки

**`P5-T07` — Отмена авторизации при истечении**
- **Описание:** потребитель `BookingExpired` → void авторизации.
- **Зависит:** P5-T06, P4-T20
- **Файлы:** `services/payment/application/consumers/booking_expired.py`
- **Готово:** после истечения удержания средства не удерживаются на карте; void идемпотентен
- **Тесты:** интеграционные на отмену и на повтор
- **Ограничения:** D14

**`P5-T08` — Гонка «авторизация после истечения»**
- **Описание:** в `booking` — обработка `PaymentAuthorized` для брони в `EXPIRED`: попытка повторно занять интервал; при срабатывании ограничения — публикация `PaymentVoidRequested`.
- **Зависит:** P5-T07, P4-T15
- **Файлы:** `services/booking/application/consumers/payment.py`
- **Готово:** если слот свободен — бронь подтверждается; если занят — авторизация отменяется, и клиент не остаётся ни с бронью, ни с удержанием средств
- **Тесты:** интеграционные на обе ветки (**обязательный сценарий**)
- **Ограничения:** ADR-0004 (компенсация), D12

**`P5-T09` — Исполнение отмены авторизации**
- **Описание:** потребитель `PaymentVoidRequested` → void в Stripe.
- **Зависит:** P5-T08
- **Файлы:** `services/payment/application/consumers/void_requested.py`
- **Готово:** авторизация снята, состояние платежа отражено в таблице
- **Тесты:** интеграционный на исполнение и на повтор
- **Ограничения:** D15

**`P5-T10` — Возврат при отмене брони**
- **Описание:** потребитель `BookingCancelled` с признаком возврата → refund → `PaymentRefunded`.
- **Зависит:** P5-T06, P4-T16
- **Файлы:** `services/payment/application/consumers/booking_cancelled.py`
- **Готово:** возврат выполняется однократно; для неоплаченной брони возврат не инициируется
- **Тесты:** интеграционные на возврат, на повтор, на отмену до оплаты
- **Ограничения:** D28

**`P5-T11` — Неуспешная оплата**
- **Описание:** в `booking` — потребитель `PaymentFailed`: перевод брони в `EXPIRED` и освобождение слота.
- **Зависит:** P5-T05
- **Файлы:** `services/booking/application/consumers/payment.py`
- **Готово:** слот освобождается сразу после отказа, не дожидаясь истечения TTL
- **Тесты:** интеграционный на освобождение слота
- **Ограничения:** ADR-0004

## M5.4 — Наблюдаемость и приёмка саги

**`P5-T12` — Метрики и алерты саги**
- **Описание:** метрики длительности саги, числа броней, зависших в `HELD` сверх TTL, неуспешных вебхуков; правила алертов.
- **Зависит:** P5-T11
- **Файлы:** `services/payment/infrastructure/metrics.py`, `deploy/local/prometheus/rules/payment.yml`
- **Готово:** остановка любого потребителя саги приводит к алерту в пределах минут
- **Тесты:** прогон с отключённым потребителем
- **Ограничения:** D8

**`P5-T13` — Сквозные тесты саги**
- **Описание:** e2e-набор по всем ветвям: успех, отказ карты, истечение, гонка, отмена с возвратом, повторная доставка вебхука.
- **Зависит:** P5-T12
- **Файлы:** `tests/e2e/saga/`
- **Готово:** ни один сценарий не оставляет списанных денег без подтверждённой брони и подтверждённой брони без денег
- **Тесты:** e2e — единственная область, где они применяются (D59)
- **Ограничения:** D59, ADR-0004

**`P5-T14` — Доставка сервиса**
- **Описание:** секреты Stripe, конвейер, дашборд саги, маршрут вебхука через Ingress, локальная переадресация вебхуков.
- **Зависит:** P5-T13
- **Файлы:** `deploy/`, `.github/workflows/`
- **Готово:** вебхук доходит до сервиса в локальном кластере; секреты зашифрованы
- **Тесты:** —
- **Ограничения:** D52, D51

# Фаза 6 — `notification`

Цель: замкнуть пользовательский путь и продемонстрировать потребителя, чья
недоступность не влияет на основной домен.

## M6.1 — Каналы и шаблоны

**`P6-T01` — Каркас сервиса**
- **Описание:** генерация из шаблона, база `notification`, таблицы `notifications` и `templates`, манифесты. Публичного API нет.
- **Зависит:** P2-T13
- **Файлы:** `services/notification/`
- **Готово:** сервис развёрнут, наружу не опубликован
- **Тесты:** smoke
- **Ограничения:** ADR-0001

**`P6-T02` — Интерфейс канала и email**
- **Описание:** абстракция канала доставки и реализация через SMTP (локально Mailhog).
- **Зависит:** P6-T01
- **Файлы:** `services/notification/domain/channel.py`, `infrastructure/channels/email.py`
- **Готово:** письмо доходит до Mailhog; ошибка SMTP приводит к ретраю, а не к потере
- **Тесты:** интеграционные на доставку и на ошибку транспорта
- **Ограничения:** ADR-0010

**`P6-T03` — Адаптеры SMS и push**
- **Описание:** реализации того же интерфейса без реального провайдера, с логированием и метрикой.
- **Зависит:** P6-T02
- **Файлы:** `services/notification/infrastructure/channels/`
- **Готово:** канал переключается конфигурацией без изменения кода сценариев
- **Тесты:** unit на выбор канала
- **Ограничения:** ADR-0010 (заглушки осознанны)

**`P6-T04` — Шаблоны**
- **Описание:** таблица шаблонов с ключом «код + канал + локаль», сид базового набора, рендеринг с экранированием.
- **Зависит:** P6-T02
- **Файлы:** `services/notification/application/render.py`, `infrastructure/db/seed.py`
- **Готово:** отсутствующий шаблон даёт внятную ошибку и попадание в DLQ, а не молчание; подстановка экранируется
- **Тесты:** unit на рендеринг и экранирование; интеграционный на отсутствующий шаблон
- **Ограничения:** D50

## M6.2 — Потребление событий

**`P6-T05` — События броней**
- **Описание:** потребители `BookingConfirmed`, `BookingCancelled`, `BookingRescheduled`, `BookingExpired`, `BookingNoShow`, `BookingCompleted`.
- **Зависит:** P6-T04, P5-T05
- **Файлы:** `services/notification/application/consumers/booking.py`
- **Готово:** каждое событие порождает ровно одно уведомление; повтор события не даёт второго письма
- **Тесты:** интеграционные на каждое событие и на дубликат
- **Ограничения:** D18

**`P6-T06` — События учётных записей**
- **Описание:** потребители `UserRegistered`, `SpecialistInvited`, `SpecialistRoleGranted`, `OrganizationCreated`.
- **Зависит:** P6-T05, P3-T05
- **Файлы:** `services/notification/application/consumers/identity.py`
- **Готово:** приглашённый специалист получает письмо со ссылкой на завершение регистрации
- **Тесты:** интеграционные на приглашение существующего и нового пользователя
- **Ограничения:** D34

**`P6-T07` — Напоминания**
- **Описание:** планирование уведомлений за 24 и 2 часа по `BookingConfirmed`, снятие запланированных по `BookingCancelled` и перепланирование по `BookingRescheduled`.
- **Зависит:** P6-T05, P2-T10
- **Файлы:** `services/notification/jobs/reminders.py`
- **Готово:** по отменённой брони напоминание не уходит; при переносе уходит по новому времени; бронь, созданная менее чем за 2 часа, не порождает просроченных напоминаний
- **Тесты:** интеграционные на отмену, перенос, позднюю бронь (**обязательный набор**)
- **Ограничения:** D37, D57

**`P6-T08` — Отказы доставки**
- **Описание:** ретраи с возрастающей задержкой, DLQ, алерт на непустую DLQ, метрика доли неуспешных доставок.
- **Зависит:** P6-T07
- **Файлы:** `services/notification/application/retry.py`, `deploy/local/prometheus/rules/notification.yml`
- **Готово:** недоступный SMTP не теряет уведомления; после исчерпания попыток запись попадает в DLQ и поднимает алерт
- **Тесты:** интеграционные на восстановление после отказа и на попадание в DLQ
- **Ограничения:** D5 (обработка отказов), D18

**`P6-T09` — Проверка изоляции отказа**
- **Описание:** сценарий: сервис остановлен во время бронирования, затем запущен.
- **Зависит:** P6-T08
- **Файлы:** `tests/e2e/notification_outage.py`
- **Готово:** бронирование и оплата проходят при остановленном сервисе; после запуска накопленные уведомления доставляются без дублей
- **Тесты:** e2e
- **Ограничения:** ADR-0001 (деградация без влияния на домен)

# Фаза 7 — Эксплуатационная зрелость

Цель: система, которую можно эксплуатировать и восстанавливать, а не только
развернуть. Фаза закрывает области, отмеченные MISSING в ревью полноты.

## M7.1 — Данные и восстановление

**`P7-T01` — Перевод баз под оператор**
- **Описание:** CloudNativePG в кластере, миграция пяти баз под управление оператора, роли и подключения через секреты.
- **Зависит:** P4-T23, P5-T14, P6-T09
- **Файлы:** `deploy/k8s/base/postgres/`
- **Готово:** все сервисы работают через кластеры оператора; данные сохранены
- **Тесты:** регресс интеграционных тестов на новой топологии
- **Ограничения:** D56, D42

**`P7-T02` — Архивация WAL и расписание бэкапов**
- **Описание:** непрерывная архивация в MinIO, регулярные базовые копии, retention.
- **Зависит:** P7-T01
- **Файлы:** `deploy/k8s/base/postgres/backup.yaml`
- **Готово:** бэкапы появляются в бакете по расписанию; объём и срок хранения заданы явно
- **Тесты:** проверка появления объектов в хранилище
- **Ограничения:** D56

**`P7-T03` — Проверка восстановления**
- **Описание:** документированная процедура восстановления на момент времени и её фактический прогон с потерей данных на тестовой базе.
- **Зависит:** P7-T02
- **Файлы:** `docs/RUNBOOK.md`
- **Готово:** база восстановлена на заданный момент, расхождение данных объяснено; процедура воспроизводима по документу без импровизации
- **Тесты:** прогон восстановления (**обязателен, иначе бэкапы считаются несуществующими**)
- **Ограничения:** D56

## M7.2 — Наблюдаемость и приёмка

**`P7-T04` — Полный набор алертов**
- **Описание:** доля 5xx, лаг потребителей, застрявший outbox, молчание sweeper и планировщика напоминаний, неуспешные вебхуки, непустая DLQ, зависшие приглашения.
- **Зависит:** P7-T01
- **Файлы:** `deploy/local/prometheus/rules/`
- **Готово:** для каждого алерта известен способ его искусственного воспроизведения, и он описан в runbook
- **Тесты:** прогон воспроизведения каждого алерта
- **Ограничения:** D8, D32

**`P7-T05` — Дашборды**
- **Описание:** дашборд на сервис и отдельный дашборд саги оплаты (воронка статусов, длительность, компенсации).
- **Зависит:** P7-T04
- **Файлы:** `deploy/local/grafana/dashboards/`
- **Готово:** по дашборду саги видно, сколько броней находится в каждом состоянии прямо сейчас
- **Тесты:** —
- **Ограничения:** D8

**`P7-T06` — Нагрузочная приёмка**
- **Описание:** прогон профиля из целевых показателей: 50 rps на доступность, конкурентное бронирование.
- **Зависит:** P7-T05, P4-T24
- **Файлы:** `tests/load/`
- **Готово:** p95 доступности < 300 мс, p95 создания брони < 500 мс; при недостижении зафиксирована причина и решение
- **Тесты:** прогон по расписанию
- **Ограничения:** D32

**`P7-T07` — Проверки отказов**
- **Описание:** поочерёдная остановка Kafka, Redis, `payment`, `notification`, базы одного сервиса; фиксация фактического поведения.
- **Зависит:** P7-T06
- **Файлы:** `docs/RUNBOOK.md`
- **Готово:** для каждого компонента задокументировано, что деградирует, что продолжает работать и что происходит после восстановления; расхождения с ожиданиями из ADR исправлены или зафиксированы
- **Тесты:** прогон каждого сценария
- **Ограничения:** ADR-0001, D25, D5

## M7.3 — Безопасность и завершение

**`P7-T08` — Периметр**
- **Описание:** ограничение частоты на Ingress, сетевые политики между namespace, запрет прямого доступа к сервисам в обход Ingress.
- **Зависит:** P7-T01

- **Тесты:** прогон обоих сценариев
- **Ограничения:** D47, D26

**`P7-T09` — Сканирование в конвейере**
- **Описание:** проверка образов и зависимостей на уязвимости, блокировка сборки при критических находках.

- **Тесты:** прогон с подставленной уязвимостью
- **Ограничения:** D60

**`P7-T10` — Ротация ключей подписи**
- **Описание:** фактический прогон ротации пары ключей с периодом перекрытия и без разлогина пользователей.
- **Зависит:** P7-T08, P1-T15

- **Готово:** во время ротации токены, выпущенные старым ключом, продолжают приниматься до истечения TTL; процедура описана по шагам
- **Тесты:** прогон ротации с активными сессиями
- **Ограничения:** D53

**`P7-T11` — Runbook и синхронизация документации**
- **Описание:** сборка runbook (реакция на каждый алерт, восстановление, ротация ключей, перестроение проекции), сверка документации с фактической реализацией.
- **Зависит:** P7-T10
- **Файлы:** `docs/RUNBOOK.md`, `docs/*`
- **Готово:** каждое расхождение между ADR и реализацией либо исправлено в коде, либо оформлено новым ADR; ни одно не оставлено молча
- **Тесты:** —
- **Ограничения:** ADR не редактируется после принятия (ADR-0000)
