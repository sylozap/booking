# ADR-0005: Событийная интеграция — outbox, доменные события, идемпотентность

- **Статус:** Принято
- **Решения:** D18, D19, D23

## Контекст

Сервисы владеют собственными БД и не имеют межсервисных внешних ключей. Интеграция —
асинхронная через брокер. Наивная схема «сохранили в БД, затем отправили в брокер»
неатомарна: падение между операциями даёт либо потерянное событие, либо событие о
несостоявшемся изменении. В системе с деньгами оба варианта неприемлемы.

## Решение

1. **Transactional outbox.** Событие пишется в таблицу `outbox` в той же транзакции,
   что и изменение состояния. Отдельный relay-процесс публикует неотправленные
   строки. Публикация в брокер из бизнес-кода запрещена.
2. **Публикуется доменный смысл, а не строки таблиц.** `catalog` отдаёт
   `OfferingUpdated` с уже разрешёнными эффективными значениями цены и длительности;
   `booking` не знает о таблице `specialist_services`.
3. **Идемпотентность обязательна на трёх контурах:** создание брони (клиентский
   `Idempotency-Key`), вебхуки Stripe (`provider_event_id`), потребление событий
   (`processed_events`).
4. **Ключ партиционирования — `specialist_id`**: строгий порядок событий по одному
   специалисту при сохранении параллелизма между специалистами.
5. **Tolerant reader:** потребитель игнорирует неизвестные поля. Несовместимые
   изменения выкатываются публикацией двух версий события параллельно.
6. **Dead letter topic** для событий, не обработанных после N попыток.

## Рассмотренные альтернативы

**Прямая публикация в брокер из бизнес-логики.** Отвергнуто: неатомарность.

**Change Data Capture (Debezium) вместо outbox.** Убирает relay-процесс и даёт
гарантии на уровне WAL. Отвергнуто: тянет Kafka Connect и заметный объём эксплуатации
для одного человека, а публиковать всё равно нужно доменные события, а не diff строк —
то есть outbox-таблица понадобится и здесь.

**Синхронные HTTP-вызовы вместо событий.** Отвергнуто: связывает доступность сервисов
(падение `notification` роняло бы создание брони) и возвращает распределённый монолит.

**At-most-once вместо идемпотентности.** Отвергнуто: потеря события об оплате.

## Последствия

**Приобретаем:** атомарность «состояние + событие»; устойчивость к дубликатам,
которые при at-least-once гарантированы; независимость доступности сервисов.

**Платим:** relay-процесс и таблица `outbox` в каждом сервисе; eventual consistency
как норма (проекция `offerings` отстаёт на десятки миллисекунд); необходимость
следить за размером `outbox` и лагом потребителей; отладка усложняется — без
распределённой трассировки путь запроса невосстановим.
