# ADR-0016: Внутренняя структура сервиса и топология данных

- **Статус:** Принято
- **Решения:** D39, D40, D41, D42

## Контекст

Пять сервисов пишет один человек. Без единой внутренней структуры каждый сервис
получится своим, и переключение между ними станет дороже, чем сама разработка.
Отдельно требуется решить изоляцию тенантов, стратегию идентификаторов и физическое
размещение баз данных на локальной машине.

## Решение

1. **Единая слоистость во всех сервисах:**
   `api/` (роутеры, схемы запросов и ответов) → `application/` (сценарии, оркестрация)
   → `domain/` (сущности, правила, доменные исключения) → `infrastructure/`
   (репозитории, брокер, внешние клиенты). Зависимости направлены только внутрь;
   `domain` не импортирует ничего из остальных слоёв.
2. **Изоляция тенантов — на уровне приложения:** `tenant_id` в каждой таблице и
   обязательная фильтрация в репозиториях. Row Level Security не используется.
3. **Идентификаторы — UUID v7.**
4. **Локальная топология БД:** один экземпляр PostgreSQL, пять отдельных баз и пять
   отдельных ролей. Cross-database запросы запрещены; строка подключения каждого
   сервиса вынесена в конфигурацию.

## Рассмотренные альтернативы

**Row Level Security.** Даёт защиту от ошибки фильтрации на уровне БД. Отвергнуто:
усложняет пул соединений (требуется установка контекста сессии на каждое соединение)
и миграции; при одном разработчике цена выше выгоды. Риск покрывается обязательными
тестами на межтенантный доступ.

**UUID v4.** Отвергнуто: случайные ключи фрагментируют B-tree и ухудшают локальность
вставки. UUID v7 сохраняет монотонность по времени.

**Автоинкрементные `bigint`.** Отвергнуто: идентификаторы пересекают границы сервисов
в событиях, и глобальная уникальность важнее компактности.

**Пять отдельных экземпляров PostgreSQL.** Физическая изоляция, максимально близкая к
production. Отвергнуто для локальной среды: пять экземпляров рядом с Kafka, Redis и
стеком наблюдаемости не оставляют ресурсов на сами сервисы. Логическая изоляция
(отдельные базы и роли, запрет cross-database) сохраняет все архитектурные свойства
database-per-service; разделение на отдельные экземпляры возможно изменением
конфигурации без изменения кода.

**Плоская структура сервиса без слоёв.** Отвергнуто: доменные правила
(инвариант непересечения, машина состояний) должны быть тестируемы без БД и брокера.

## Последствия

**Приобретаем:** одинаковую навигацию по всем сервисам; тестируемый в изоляции домен;
экономию ресурсов локальной среды без потери архитектурных свойств.

**Платим:** пропущенная фильтрация по `tenant_id` не будет остановлена базой — это
класс ошибок, закрываемый только тестами и ревью; общий экземпляр PostgreSQL — общая
точка отказа локально, что расходится с production-топологией.
