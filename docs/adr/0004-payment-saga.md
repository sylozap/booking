# ADR-0004: Оплата — авторизация с отложенным списанием, оркестрируемая сага

- **Статус:** Принято
- **Решения:** D9, D14, D15, D28, D29

## Контекст

Клиент оплачивает бронь в момент создания, деньги проходят через платформу
(комиссия — источник дохода). Создание брони и приём платежа физически находятся в
разных сервисах и разных БД, а Stripe — внешняя система с собственной моделью
отказов и асинхронными вебхуками. Единой транзакции не существует.

Слот должен быть защищён на время оплаты, иначе клиент оплатит уже занятое время.

## Решение

**Модель денег: authorize при удержании, capture при подтверждении, void при отмене
удержания.** Stripe PaymentIntent создаётся с `capture_method=manual`.

**Оркестрируемая сага, координатор — `booking`:**

1. `POST /bookings` → `HELD`, слот защищён `EXCLUDE`, TTL 15 минут;
2. `BookingHeld` → `payment` создаёт PaymentIntent, авторизует средства;
3. `PaymentAuthorized` → `booking` переводит бронь в `CONFIRMED`;
4. `BookingConfirmed` → `payment` выполняет capture;
5. `PaymentFailed` или истечение TTL → `EXPIRED`, авторизация отменяется.

**Компенсация при гонке:** если `PaymentAuthorized` приходит для уже истёкшей брони,
`booking` пытается повторно занять интервал; при срабатывании `EXCLUDE` публикуется
`PaymentVoidRequested` и авторизация отменяется.

**Политики:** отмена клиентом — не позже `min_lead_time` до начала, полный возврат;
отмена специалистом — в любой момент, полный возврат; `NO_SHOW` проставляется
специалистом вручную, возврат не производится.

## Рассмотренные альтернативы

**Немедленное списание вместо авторизации.** Проще в реализации. Отвергнуто: каждый
неуспешный сценарий превращается в возврат — комиссия за refund, дни ожидания у
клиента, строчка в отчётности. Отмена авторизации не является движением денег.

**Хореография без координатора.** Сервисы реагируют на события друг друга без
центральной точки. Отвергнуто: таймаут удержания слота принципиально принадлежит
брони; размазав его по сервисам, теряем контроль над жизненным циклом и
возможность ответить на вопрос «в каком состоянии сага прямо сейчас».

**Оркестратор в `payment`.** Отвергнуто: `payment` не должен знать о существовании
броней — иначе он становится доменным сервисом бронирования с платёжным адаптером.

**Двухфазный коммит между сервисами.** Отвергнуто: Stripe в нём участвовать не может.

## Последствия

**Приобретаем:** слот защищён на время оплаты; неуспешные оплаты не порождают
движения денег; состояние саги в любой момент читается как статус брони.

**Платим:** обязательный фоновый sweeper истёкших удержаний; необходимость обрабатывать
гонку «оплата после истечения»; авторизация Stripe живёт ограниченное время (порядка
7 дней), что делает невозможной модель «бронь сейчас — оплата сильно позже»;
частично оплаченные состояния существуют в системе и требуют мониторинга.
