# ADR-0009: Порядок реализации, service chassis и инфраструктура доставки

- **Статус:** Принято
- **Решения:** D6, D7, D10

## Контекст

Пять сервисов пишет один человек. Типичный сценарий провала: сначала пишутся все
сервисы, затем «добавляется мониторинг». Инструментирование, трассировка, outbox и
единый формат ошибок так не добавляются — их приходится вносить в каждый сервис
задним числом, и обычно не вносят.

Развёртывание локальное; CI не имеет сетевого доступа внутрь машины разработчика.

## Решение

1. **Вертикальный срез первым.** `identity` доводится до полного production-состояния:
   Dockerfile, миграции, healthchecks, структурные логи, метрики, трассировка, тесты,
   CI-пайплайн, деплой в кластер.
2. **Из него извлекается service chassis** — внутренняя библиотека с cross-cutting
   инфраструктурой (логирование, OTel, аутентификация, outbox, идемпотентное
   потребление, конфигурация, health, формат ошибок).
3. **Остальные сервисы строятся на шасси** и стоят кратно дешевле.
4. **В шасси только инфраструктура.** Доменные модели и DTO чужих сервисов запрещены;
   дублирование доменных типов между сервисами — это изоляция, а не дефект.
5. **Кластер:** kind или k3d локально.
6. **CI:** GitHub Actions — линт, тесты, сборка образа, публикация в ghcr.io,
   обновление тега образа в манифестах.
7. **CD:** ArgoCD внутри кластера тянет манифесты из репозитория (GitOps).

## Рассмотренные альтернативы

**Полное дублирование инфраструктурного кода вместо шасси.** Максимальная
независимость сервисов, ноль связности. Отвергнуто: пятикратная настройка
OpenTelemetry и outbox одним человеком не будет выполнена — на практике это означает,
что часть сервисов останется без телеметрии.

**Шасси, включающее общие доменные модели.** Отвергнуто: превращает микросервисы в
монолит с общим релизным циклом — изменение модели требует одновременного обновления
всех сервисов.

**Горизонтальный порядок работ** (сначала все API, затем вся инфраструктура).
Отвергнуто: инфраструктура откладывается до момента, когда её внедрение стоит в пять
раз дороже.

**`kubectl apply` из CI вместо GitOps.** Проще. Отвергнуто: требует доступа пайплайна
внутрь локальной сети, а состояние кластера перестаёт быть воспроизводимым из
репозитория.

**Docker Compose вместо Kubernetes.** Существенно дешевле для одного человека.
Отвергнуто осознанно: освоение Kubernetes входит в цели проекта. Compose
сохраняется для локальной разработки отдельных сервисов.

## Последствия

**Приобретаем:** каждый следующий сервис дешевле предыдущего; телеметрия и outbox
существуют с первого дня; состояние кластера воспроизводимо из репозитория.

**Платим:** шасси — точка связности, её ломающее изменение затрагивает все сервисы;
первый сервис делается заметно дольше остальных, и на этом этапе легко потерять
мотивацию; ArgoCD, брокер и стек наблюдаемости потребляют ресурсы локальной машины
сопоставимо с самими сервисами.

## Дополнение: структура репозитория (D30)

**Монорепозиторий** — все сервисы, шасси, манифесты и документация в одном
репозитории.

Альтернатива — репозиторий на сервис. Отвергнута: для одного разработчика она даёт
только издержки — синхронизация изменений шасси через публикацию пакета,
рассинхронизация версий, отсутствие атомарного изменения контракта и его потребителя.
Независимость релизных циклов, ради которой существует polyrepo, ценна при
нескольких командах.

Цена монорепо: требуется дисциплина, чтобы общий репозиторий не превратился в общий
код. Обеспечивается запретом импортов между сервисами и раздельными пайплайнами
сборки по путям.
