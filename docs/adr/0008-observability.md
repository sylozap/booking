# ADR-0008: Стек наблюдаемости

- **Статус:** Принято
- **Решения:** D8

## Контекст

В распределённой системе логи отдельного сервиса не объясняют поведение запроса:
создание брони проходит через ingress, `booking`, брокер, `payment`, Stripe и
возвращается вебхуком. Без сквозной трассировки причина отказа невосстановима.

Исходно в требованиях был указан ELK/OpenSearch. Ресурсы — один локальный кластер
на машине разработчика; эксплуатирует один человек.

## Решение

OpenTelemetry как единый источник телеметрии во всех сервисах (через шасси):

- **Prometheus** — метрики (RED: rate, errors, duration; плюс доменные: длина
  очереди outbox, лаг потребителей, число `HELD` с истёкшим сроком, отказы саги);
- **Loki** — логи, структурные JSON с `trace_id`;
- **Tempo** — распределённая трассировка;
- **Grafana** — единый UI с переходами трейс → логи → метрики по `trace_id`;
- **Alertmanager** — алерты: рост 5xx, лаг потребителя, застрявший outbox,
  неуспешные вебхуки Stripe.

## Рассмотренные альтернативы

**ELK / OpenSearch.** Чаще встречается в вакансиях, мощный полнотекстовый поиск.
Отвергнуто: Elasticsearch требует нескольких гигабайт RAM, тюнинга и ILM-политик и
станет самым тяжёлым компонентом системы — тяжелее всех сервисов вместе. Для одного
разработчика это недели эксплуатации вместо архитектуры.

**Только логи, без трассировки.** Дешевле. Отвергнуто: в распределённой системе с
сагой это отказ от единственного инструмента, который делает её отлаживаемой.

**Облачное APM (Datadog, New Relic).** Отвергнуто: стоимость и отсутствие
переносимого навыка эксплуатации.

## Последствия

**Приобретаем:** ресурсно дешёвый стек (Loki индексирует метки, а не содержимое
логов); один UI; навык OpenTelemetry, переносимый на любой бэкенд, включая ELK.

**Платим:** слабый полнотекстовый поиск по логам по сравнению с Elasticsearch —
дисциплина меток становится обязательной; инструментирование должно быть заложено в
шасси с самого начала, добавить его задним числом в пять сервисов дороже, чем
написать сразу.
