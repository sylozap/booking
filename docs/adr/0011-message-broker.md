# ADR-0011: Выбор брокера сообщений

- **Статус:** Принято
- **Решения:** D31

## Контекст

Интеграция сервисов асинхронная. Требования, вытекающие из принятых решений:

1. **Порядок событий в рамках специалиста** — сага оплаты и проекция расписания
   некорректны при переупорядочивании (`BookingHeld` после `PaymentAuthorized`).
2. **Повторное воспроизведение потока** — проекция `offerings` в `booking` должна
   восстанавливаться с нуля: при добавлении сервиса, при потере проекции, при
   исправлении бага в обработчике.
3. **Независимые потребители одного потока** — `BookingConfirmed` читают и `payment`,
   и `notification`.
4. Эксплуатация одним человеком на локальной машине.

## Решение

**Apache Kafka** в режиме KRaft (без ZooKeeper).

Ключ партиционирования — `specialist_id`. Топик на тип агрегата, не на тип события.
Политика retention задаётся явно и с запасом: воспроизведение потока для перестроения
проекций возможно только в пределах retention.

## Рассмотренные альтернативы

**RabbitMQ.** Проще в эксплуатации, богатая маршрутизация, привычная модель очередей.
Отвергнуто по пункту 2: сообщение исчезает после подтверждения, воспроизвести историю
для перестроения проекции нечем. Пришлось бы либо читать исходную БД владельца
(межсервисная связность), либо хранить отдельный журнал событий — то есть строить лог
поверх брокера, у которого его нет.

**Redpanda** (единый бинарь, Kafka API, без JVM). Существенно легче по ресурсам на
локальной машине при полной совместимости клиентского кода. Отвергнуто владельцем
проекта осознанно: освоение эксплуатации самой Kafka — включая KRaft, партиции,
consumer-группы и retention — входит в цели проекта, а ресурсная цена принимается.

**PostgreSQL как очередь** (`SELECT ... FOR UPDATE SKIP LOCKED`). Ноль новых
компонентов. Отвергнуто: пришлось бы выбрать одну общую БД для очереди (нарушение
database-per-service) или связывать сервисы через чужую БД; кроме того, освоение
брокера входит в цели проекта.

**NATS JetStream.** Легче Kafka, есть персистентность и воспроизведение. Отвергнуто:
меньшая распространённость при сопоставимой сложности — навык переносится хуже.

## Последствия

**Приобретаем:** воспроизведение потока для перестроения проекций; порядок в рамках
ключа; независимые consumer-группы; эталонный, максимально «продакшеновый» опыт
эксплуатации.

**Платим:** JVM и несколько гигабайт RAM на локальной машине рядом с пятью сервисами,
пятью экземплярами PostgreSQL, Redis и стеком наблюдаемости — Kafka станет самым
тяжёлым компонентом среды разработки; партиционирование становится проектным решением,
а не деталью (изменение числа партиций меняет распределение ключей); порядок
гарантирован только внутри партиции, глобального порядка нет; политика retention
требует настройки, иначе воспроизведение окажется невозможным именно тогда, когда
понадобится.
