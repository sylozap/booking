# ADR-0012: Нефункциональные требования и целевые показатели

- **Статус:** Принято
- **Решения:** D32

## Контекст

Реальный масштаб продукта неизвестен и на момент проектирования не может быть оценён.
Однако без числовых ориентиров невозможно выставить пороги алертов, обосновать
индексы, оценить результат нагрузочного теста и понять, когда система «достаточно
быстра». Отсутствие цифр приводит к тому, что производительность не проверяется вообще.

## Решение

Принять целевые показатели как **проектные допущения**, а не как прогноз рынка.

| Параметр | Значение |
|---|---|
| Организаций / специалистов | 500 / 5 000 |
| Броней в месяц | 50 000 |
| Пик на `GET /availability` | 50 rps |
| p95 `GET /availability` | < 300 мс |
| p95 `POST /bookings` | < 500 мс |
| Активная выборка броней | 90 дней; хранение бессрочное |

Показатели являются входом для порогов алертов и критериев приёмки нагрузочного
теста (фаза 7).

Отдельное следствие: топик `OfferingUpdated` объявляется **compacted** с ключом
`(specialist_id, service_id)`. Перестроение проекции `offerings` в `booking` перестаёт
зависеть от политики retention — последнее состояние каждого ключа хранится всегда.

## Рассмотренные альтернативы

**Не фиксировать цифры до появления реальной нагрузки.** Отвергнуто: алерты без
порогов не пишутся, нагрузочный тест без критерия приёмки не имеет смысла, а
производительность, которую никто не измеряет, деградирует незаметно.

**Обычный retention вместо компактного топика для `OfferingUpdated`.** Отвергнуто:
перестроение проекции — заявленный сценарий (ADR-0005), и он обязан работать спустя
произвольное время, а не только в пределах окна хранения.

## Последствия

**Приобретаем:** проверяемые критерии производительности; независимость перестроения
проекций от retention.

**Платим:** цифры условны и при расхождении с реальностью потребуют пересмотра
алертов и, возможно, схемы; компактный топик не хранит историю изменений предложения —
только текущее состояние, поэтому аудит цен по нему невозможен.
