# Реестр решений

Все решения приняты владельцем проекта. Обоснования — в соответствующих ADR.

| ID | Решение | ADR |
|---|---|---|
| D1 | Микросервисная архитектура (жёсткое требование) | 0001 |
| D2 | `booking` и `calendar` объединены; availability — модуль, не сервис | 0001 |
| D3 | `auth` и `user` объединены в `identity` | 0001 |
| D4 | Пять сервисов: identity, catalog, booking, payment, notification | 0001 |
| D5 | Минимальный домен, полная платформа; reviews/recurring/S3 вне MVP | 0010 |
| D6 | Порядок работ: вертикальный срез → шасси → остальные сервисы | 0009 |
| D7 | В шасси только инфраструктура; доменные типы не шарятся | 0009 |
| D8 | OpenTelemetry + Prometheus/Loki/Tempo/Grafana вместо ELK | 0008 |
| D9 | Предоплата при бронировании, деньги через платформу, доход — комиссия | 0004 |
| D10 | Локальный kind/k3d, CI в GitHub Actions, CD через ArgoCD (GitOps) | 0009 |
| D11 | `Availability` — read-модель, не агрегат и не сервис | 0007 |
| D12 | Инвариант непересечения — `EXCLUDE USING gist`, буфер в интервале | 0002 |
| D13 | UTC в БД, расписание в локальном времени + IANA-зона, явный DST | 0003 |
| D14 | Stripe: authorize при удержании, capture при подтверждении, void при отмене | 0004 |
| D15 | Оркестрируемая сага, координатор — `booking` | 0004 |
| D16 | Перенос — атомарная операция внутри агрегата | 0002 |
| D17 | Рабочие часы и исключения принадлежат `booking` | 0001 |
| D18 | Идемпотентность: создание брони, вебхуки, потребление событий | 0005 |
| D19 | Database-per-service, межсервисных FK нет, outbox в каждом сервисе | 0005 |
| D20 | RBAC привязан к тенанту (`user_roles.tenant_id`) | 0006 |
| D21 | Ротация refresh-токенов с отзывом семейства при переиспользовании | 0006 |
| D22 | «Толстый» access-token, TTL 15 мин, RS256/JWKS, denylist в Redis | 0006 |
| D23 | `catalog` публикует доменное `OfferingUpdated`, не зеркало таблиц | 0005 |
| D24 | Истечение удержаний — фоновый sweeper (ленивое невозможно) | 0007 |
| D25 | Кэш доступности не участвует в записи | 0007 |
| D26 | Gateway — готовый Ingress; authn/authz в каждом сервисе | 0006 |
| D27 | grid_step 15 мин, min_lead_time 2 ч, горизонт 60 дней | 0007 |
| D28 | Отмена: клиент — до min_lead_time, специалист — всегда; полный возврат | 0004 |
| D29 | `NO_SHOW` вручную специалистом, без возврата | 0004 |
| D30 | Монорепозиторий | 0009 |
| D31 | Apache Kafka (KRaft) как брокер событий | 0011 |
| D32 | Целевые показатели как проектные допущения; `OfferingUpdated` — compacted топик | 0012 |
| D33 | Документируются 6 сквозных пользовательских сценариев | 0013 |
| D34 | Роль `SPECIALIST` выдаётся асинхронно: `SpecialistInvited` → `SpecialistRoleGranted` | 0013 |
| D35 | `CONFIRMED` → `COMPLETED` фоновой задачей через 60 мин после окончания | 0014 |
| D36 | Деактивация специалиста/услуги не отменяет существующие брони | 0014 |
| D37 | Напоминания за 24 ч и 2 ч, планирует `notification` | 0014 |
| D38 | Выплаты организациям вне MVP; комиссия — модель на бумаге | 0015 |
| D39 | Единая слоистость api → application → domain → infrastructure | 0016 |
